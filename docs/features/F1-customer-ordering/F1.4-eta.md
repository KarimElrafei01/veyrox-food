# F1.4 — ETA

The promised ready-time range shown before the customer commits.

**Traces to**: FR-2.19, FR-3.4 · NFR-12, NFR-13 · PRD §8.2, §8.3.

---

## 1. It is a promise, not a calculation

PRD §8.2's stated purpose is that the customer can *decide whether to wait*. That makes ETA a commitment, and it is graded as one:

- **A range, never a point.** "8–12 min", not "10 min". A point estimate is wrong by construction and reads as a broken promise the moment it slips by ninety seconds.
- **Accuracy is an SLI** (NFR-12), alerting when the promise is missed **or beaten** by more than 5 minutes at p90. Saying twelve and delivering in four teaches customers to ignore the number, which costs the feature its entire purpose.
- **The clock starts at Accept, not at placement.** An order sitting unaccepted in the New column has not started being made (ADR-0010). Starting the clock earlier would make the café's staffing problem look like a broken ETA.

---

## 2. The formula

`packages/domain/eta.ts` — pure, clock injected.

```
prepSeconds(cart)   = max(item.prepSeconds)
                    + 0.4 × Σ(other items' prepSeconds)      // parallelism factor
                    capped at 900

queueSeconds(state) = ( Σ remaining prep in RECEIVED
                      + Σ remaining prep in PREPARING ) / activeStations

etaSeconds          = prepSeconds + queueSeconds

display             = [ round5(eta × 0.9), round5(eta × 1.25) ]
```

| Term | Default | Notes |
|---|---|---|
| Parallelism factor | 0.4 | A barista pulls a second shot while the first steams. Owner-tunable within 0.2–0.8 (FR-10.3) |
| `activeStations` | 1 | Set on the KDS header (FR-3.10). **Never zero** — clamped, or this divides by zero |
| Remaining prep, `preparing` | Decays linearly from the item's estimate | A ticket 60s into a 150s drink contributes 90s, not 150s |
| Range | ×0.9 to ×1.25 | Deliberately asymmetric. Over-running hurts more than finishing early |

**Under-promising is a product decision.** The asymmetric range is not hedging — it is choosing which error to make.

## 3. API

ETA is never fetched alone. It rides on the quote (F1.3) and the confirmation, because a standalone endpoint would be polled — and polling is banned (ADR-0005).

**In `POST /public/orders/quote`:**

```json
{ "eta": { "lowerMinutes": 8, "upperMinutes": 12, "queueDepth": 3 } }
```

**In `POST /public/orders` (F1.6) and `GET /public/orders/:id/status` (F1.7):**

```json
{
  "eta": {
    "lowerMinutes": 8,
    "upperMinutes": 12,
    "promisedLowerAt": "2026-09-06T15:39:00+03:00",
    "promisedUpperAt": "2026-09-06T15:43:00+03:00",
    "startsOnAccept": true
  }
}
```

Before Accept, `promisedLowerAt`/`promisedUpperAt` are `null` and `startsOnAccept` is `true`. The webview shows "≈8–12 min once the kitchen accepts" rather than a wall-clock time it cannot yet honour.

Once accepted, the timestamps are fixed and written to `orders.promised_eta_lower_at` / `promised_eta_upper_at`. **They are never recomputed** — that snapshot is what NFR-12 measures against, and a moving promise is unmeasurable.

## 4. Queue state — the scalability point

Queue depth is read on **every quote**, i.e. every cart change. Counting rows per request would be the one gratuitous hot query in F1.

So queue state is **maintained in Redis by the domain event bus**, not computed on read:

```
Key:   queue:{tenantId}
Value: { activeStations: 1,
         tickets: [ { orderId, prepSeconds, status, startedAt } ],
         updatedAt }
TTL:   300s   (backstop only)
```

Updated on `OrderAccepted`, `OrderPreparing`, `OrderReady`, `OrderVoided`, `OrderAbandoned`, `ActiveStationsChanged` — the same events that drive the SSE stream (ADR-0005). One event bus feeds both the KDS board and the ETA, so **the number the customer sees and the number on the board come from one source**, which is PRD §8.3's actual requirement.

**Rebuild on miss** — one indexed query, and this is why the index is partial:

```sql
SELECT id, status, accepted_at, prep_seconds
FROM orders
WHERE tenant_id = $1 AND status IN ('received','preparing');

-- orders (tenant_id, status) WHERE status IN ('placed','received','preparing')
```

The partial predicate keeps that index at a few dozen rows forever — completed orders drop out of it — so even the cold path is an index-only scan independent of how much history the café has.

**Failure mode**: if Redis is unavailable, fall back to the direct query. If *that* fails, return `queueSeconds = 0` and widen the range to ×1.5, with a log line. **A pessimistic ETA is always better than no ETA** — the customer can still decide.

## 5. Calibration (v2, Sprint 9)

`menu_items.prep_seconds` starts as an owner-entered estimate and is wrong within a week. The `eta.calibrate` job (03:30 Cairo, `01-system-design.md` §6) replaces it nightly with the **observed p50 of `ready_at − accepted_at`**, bucketed by item and hour-of-day.

Guards: minimum 30 observations before replacing a value; changes clamped to ±30% per night; the owner-entered value is retained as a floor. Without those, one anomalous morning drags the estimate somewhere it should not go.

Until calibration ships, the static estimate is used and NFR-12 is expected to sit outside target. That is a known, dated gap — not a surprise.

## 6. Edge cases

| Case | Behaviour |
|---|---|
| `activeStations = 0` | Clamped to 1. Division by zero is the classic ETA crash |
| Empty queue | `queueSeconds = 0`. ETA is prep time alone |
| Very large cart | `prepSeconds` capped at 900 (15 min). Beyond that the estimate is fiction anyway |
| Gold priority prep (FR-2.22) | Gold tickets sort first, so a Gold order's queue wait excludes non-Gold tickets behind it |
| Order voided while queued | Event removes it from queue state immediately |
| Ticket stuck in `preparing` | Remaining prep floors at 0 — it never contributes negative time |
| Redis down | Direct query, then `queueSeconds = 0` with a widened range |
| Clock skew across API instances | ETA is computed server-side only, from one injected clock. Clients never compute it |

## 7. Observability

| Signal | Purpose |
|---|---|
| `eta_error_seconds` | `actual_ready_at − promised_upper_at`, recorded on every completed order. **The NFR-12 SLI** |
| `eta_queue_depth` | Gauge, on the Café Health dashboard |
| `eta_cache_miss_total` | Counter. A rising rate means the event bus is dropping updates |
| `eta_fallback_total` | Counter. Any non-zero value is a ticket — it means customers got a degraded promise |

---

## 8. Tests

**Unit** (100% branch): single item; large cart at the cap; empty queue; deep queue; **zero active stations**; range rounding at 5-minute boundaries; linear decay of in-progress prep; Gold priority excluding lower-tier tickets.

**Property**: ETA is monotonic — adding an item never *decreases* the estimate. Cheap to state, and it catches sign errors in the parallelism term.

**Integration**: accepting an order updates Redis queue state and the next quote reflects it; a cold Redis rebuilds identically from Postgres; Redis-down returns the widened fallback rather than an error.
