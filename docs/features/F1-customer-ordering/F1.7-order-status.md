# F1.7 — Order Status

What the customer sees after placing, until they collect.

**Traces to**: FR-2.18, FR-3.2 · ADR-0005 (no polling) · ADR-0010 (accept gate).

---

## 1. WhatsApp is the status channel, not the webview

The customer places the order and puts their phone away. **The messages are the product surface after placement**, not the webview:

| Moment | Message | Rail |
|---|---|---|
| Placed | *(none — the 201 response is the acknowledgement)* | — |
| **Accepted** | Confirmation: ETA range, order number, itemised total, **"pay at the counter when you collect"**, points to be earned | Official |
| **Ready** | "Your order is ready" | Official |
| Rejected | Polite decline with the reason | Official |
| T+30m after collection | Review request | Official (F4) |

**The confirmation fires on Accept, not on placement.** Sending an ETA before a barista has accepted would promise a time the kitchen has not committed to (F1.4 §1). A customer who places at 08:41 and is accepted at 08:42 gets one message, correctly timed.

The endpoint below exists for the narrow case of the customer still having the webview open — not as the primary channel.

### Placement receipt in the webview

Immediately after a successful placement, the webview keeps a display-only snapshot of its
cart lines, modifiers, images, quote breakdown, and points-to-earn in `sessionStorage`, keyed
by order id. This supplies the expanded receipt on the confirmation screen without extending
the status endpoint. It is not a source of truth: the status endpoint remains authoritative for
status, ETA, and total, and the snapshot disappears when the browser tab closes.

The loyalty panel displays the current session balance and says that the quoted points **will be
added on collection**. It must never say points were added at placement (F1.5 §2; FR-2.20).

## 2. API

### `GET /public/orders/:orderId/status`

Session token required; the token's customer must own the order.

**Response 200 — placed, awaiting Accept**

```json
{
  "orderId": "o_9f2…",
  "orderNumber": "A-047",
  "status": "placed",
  "statusLabel": { "en": "Sent to the kitchen", "ar-EG": "تم الإرسال للمطبخ" },
  "totalMinor": 27500,
  "payAt": "counter",
  "eta": { "lowerMinutes": 8, "upperMinutes": 12, "startsOnAccept": true,
           "promisedLowerAt": null, "promisedUpperAt": null },
  "loyalty": { "pointsToEarn": 33 },
  "placedAt": "2026-09-06T15:31:12+03:00",
  "traceId": "0af7651916cd43dd"
}
```

**Response 200 — accepted, clock running**

```json
{
  "status": "received",
  "statusLabel": { "en": "Being prepared", "ar-EG": "جاري التحضير" },
  "eta": { "lowerMinutes": 6, "upperMinutes": 9, "startsOnAccept": false,
           "promisedLowerAt": "2026-09-06T15:39:00+03:00",
           "promisedUpperAt": "2026-09-06T15:43:00+03:00" },
  "acceptedAt": "2026-09-06T15:32:04+03:00"
}
```

`promisedLowerAt`/`promisedUpperAt` are the **snapshot written at Accept** and are never recomputed — that fixed promise is what NFR-12 measures against. `lowerMinutes`/`upperMinutes` are derived from it against the current clock, so they count down.

**Response 200 — rejected**

```json
{
  "status": "rejected",
  "statusLabel": { "en": "Could not be prepared", "ar-EG": "تعذّر التحضير" },
  "rejectionReason": "item_unavailable",
  "rejectedAt": "2026-09-06T15:33:10+03:00"
}
```

Reason codes: `too_busy` · `item_unavailable` · `closing`. Never a free-text staff note — that is internal.

**Errors**: `404 ORDER_NOT_FOUND` (also returned when the order belongs to another customer — never confirm existence), `401 SESSION_*`.

## 3. Status vocabulary shown to customers

Internal statuses are not customer language. The mapping is deliberate:

| Internal | Customer sees | Why |
|---|---|---|
| `placed` | "Sent to the kitchen" | Honest — not yet accepted, but not alarming |
| `received` | "Being prepared" | Accepted; the clock is running |
| `preparing` | "Being prepared" | **Same label.** The internal distinction is a KDS column, not customer-relevant |
| `ready` | "Ready for collection" | |
| `collected` | "Collected" | Terminal |
| `rejected` | "Could not be prepared" | With reason |
| `voided` | "Cancelled" | Staff-initiated |
| `abandoned` | "Not collected" | Terminal, no blame in the wording |

Collapsing `received` and `preparing` is intentional: exposing every internal transition invites *"why has it said Received for four minutes?"* — a question about our state machine, not about their coffee.

---

## 4. No polling

The webview does **not** poll this endpoint (ADR-0005). Behaviour when the customer keeps it open:

- Fetch once on placement, then once on window focus.
- After that, the webview shows a static "we'll message you when it's ready" panel.
- **The ready ping is a WhatsApp message**, which is exactly what lets the customer put the phone away — the whole product benefit.

A customer-facing SSE stream was considered and rejected: it would hold a connection per browsing customer for a status they have already been promised by message, against an API that cannot scale to zero because of the staff streams it already holds (ADR-0011 §"One constraint").

## 5. Data access and caching

One indexed point lookup by primary key, plus an ownership check on `customer_id` from the token.

```sql
SELECT id, order_number, status, total_minor,
       promised_eta_lower_at, promised_eta_upper_at,
       placed_at, accepted_at, ready_at, collected_at,
       rejection_reason
FROM orders
WHERE id = $1 AND tenant_id = $2 AND customer_id = $3;
```

No new index needed — this is the primary key with two predicate columns.

**Not cached.** The response is per-customer and status-volatile, and the call volume is negligible because nothing polls it. Caching would add invalidation complexity to protect a query that runs a handful of times per order.

`statusLabel` is resolved server-side from `packages/i18n` rather than mapped client-side, so the customer's language choice is honoured even in a message-driven flow where no client is rendering.

## 6. Edge cases

| Case | Behaviour |
|---|---|
| Order belongs to another customer | `404`, not `403`. Never confirm an order id exists |
| Session expired, webview still open | `401 SESSION_EXPIRED`. The WhatsApp messages continue regardless — they do not depend on a session |
| Order abandoned while the webview is open | Status flips to `abandoned`. No materials return; it is waste (ADR-0010) |
| Rejected before the customer reads anything | The rejection message is the notification; the endpoint is consistent with it |
| Accepted while the response is in flight | Whatever committed wins. Both shapes are valid |
| Clock skew on the device | All countdowns derive from server timestamps, never from device time |

---

## 7. Tests

**Integration**: each status returns the correct label in both locales; ownership check returns `404` for another customer's order; `promisedUpperAt` is written once at Accept and unchanged by later transitions.

**Unit**: countdown derivation from `promisedUpperAt` across the boundary where it goes negative — it must floor at zero, not display "-2 min".

**E2E** (journey 2): place → Accept → confirmation message received → Ready → ready message received, with the status endpoint agreeing at each step.
