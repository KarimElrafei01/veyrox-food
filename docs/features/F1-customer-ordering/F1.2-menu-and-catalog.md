# F1.2 — Menu & Catalog

Serving the menu to the webview: categories, items, modifier groups, prices, and live availability.

**Traces to**: FR-2.6–2.10, FR-10.12 (draft/publish) · PRD §8.2.

---

## 1. The split — the central decision

The menu is the hottest read in the system and almost entirely static. Availability changes several times a day and must be current within seconds. **Serving both from one endpoint drags the whole payload down to availability's TTL and throws away the caching win.**

So there are two endpoints:

| | `GET /public/menu/:menuVersion` | `GET /public/availability` |
|---|---|---|
| Content | Categories, items, modifiers, **prices** | Two ID lists: 86'd items, 86'd modifier options |
| Volatility | **Immutable** — a version is never mutated | Seconds |
| Size | 20–80 KB gzipped | Typically < 1 KB |
| Cache | `public, max-age=31536000, immutable` | `public, max-age=5, stale-while-revalidate=30` |
| Served by | **CDN edge — zero API, zero DB** | API + Redis |

Because the version is in the **path**, publishing a revision (FR-10.12) mints a new URL. **There is no cache invalidation to get wrong** — the class of bug where a café changes a price and customers keep seeing the old one simply cannot occur. Sessions pinned to an older version keep resolving it, which is exactly what FR-2.2 requires.

The client fetches both on load and merges. On window focus it re-fetches **availability only**.

## 2. API

### `GET /public/menu/:menuVersion`

No auth — the payload is a café's public menu, and requiring a token would defeat CDN caching for zero security gain. The version id is an unguessable UUID.

**Response 200** (`Cache-Control: public, max-age=31536000, immutable`, `ETag`)

```json
{
  "menuVersion": "8a2e…",
  "publishedAt": "2026-09-01T09:12:00+03:00",
  "categories": [
    {
      "id": "c1…", "sort": 1,
      "name": { "en": "Espresso", "ar-EG": "إسبريسو" },
      "items": [
        {
          "id": "i1…", "sort": 1,
          "name": { "en": "Latte", "ar-EG": "لاتيه" },
          "description": { "en": "Double shot, steamed milk", "ar-EG": "…" },
          "basePriceMinor": 9000,
          "prepSeconds": 150,
          "imageUrl": null,
          "modifierGroupIds": ["g_size", "g_milk"]
        }
      ]
    }
  ],
  "modifierGroups": [
    {
      "id": "g_milk",
      "name": { "en": "Milk", "ar-EG": "لبن" },
      "selection": "single",
      "required": true,
      "minSelect": 1,
      "maxSelect": 1,
      "options": [
        { "id": "m_whole", "name": { "en": "Whole", "ar-EG": "كامل الدسم" },
          "priceDeltaMinor": 0,     "freeForTier": null,   "sort": 1 },
        { "id": "m_oat",   "name": { "en": "Oat",   "ar-EG": "شوفان" },
          "priceDeltaMinor": 1500,  "freeForTier": "silver", "sort": 2 }
      ]
    }
  ]
}
```

Notes on shape:

- **Modifier groups are top-level and referenced by id**, not nested per item. "Milk" attaches to twelve drinks; nesting would repeat it twelve times and roughly double the payload against a hard 150 KB budget (NFR-9).
- **Names are locale maps**, resolved client-side. One cached artefact serves both languages — two localized payloads would double CDN entries and halve hit rate. `ar-EG` falls back to `en` when absent (FR-9.1).
- **`freeForTier`** is data, not logic: the client renders the delta struck through for an eligible tier, and the server applies the same rule independently at quote time (F1.3 §3). Never trust the client's rendering.
- **No availability here.** Deliberately.

### `GET /public/availability`

Auth: session token (it is tenant-scoped and tiny; no CDN value in making it public).

**Response 200** (`Cache-Control: public, max-age=5, stale-while-revalidate=30`)

```json
{
  "menuVersion": "8a2e…",
  "unavailableItemIds": ["i7…", "i9…"],
  "unavailableModifierOptionIds": ["m_oat"],
  "asOf": "2026-09-06T15:31:04+03:00"
}
```

**A denylist, not an allowlist.** A café 86s two or three things on a busy day; listing what is *available* would mean shipping the whole catalogue again on a five-second TTL. The denylist is near-empty in the normal case.

`menuVersion` is echoed so a client can detect it is holding a stale menu against fresh availability and re-resolve its session.

## 3. Data access

Both endpoints are cache-first. The database is touched only on a miss.

**Menu assembly** (cold path only — once per version, then never again):

```sql
menu_items                (tenant_id, category_id, sort) WHERE active
menu_item_prices          (tenant_id, menu_item_id) WHERE valid_to IS NULL
modifier_options          (tenant_id, group_id, sort) WHERE active
menu_item_modifier_groups (menu_item_id, sort)
```

The price index is **partial on `valid_to IS NULL`**, so resolving the current price of every item is an index-only scan over exactly one row per item — regardless of how many historical versions have accumulated. Without the partial predicate this degrades steadily as a café edits prices over the years.

**Availability** (hot path, but trivial):

```sql
menu_items       (tenant_id) WHERE NOT is_available
modifier_options (tenant_id) WHERE NOT is_available
```

Both partial indexes cover only the 86'd rows — typically single digits — so the query reads a handful of tuples.

## 4. Caching

| Layer | Key | TTL | Invalidated by |
|---|---|---|---|
| CDN | `/public/menu/:version` | Immutable | Never. New version = new URL |
| Redis | `menu:{tenantId}:{version}` | 24h | Never (immutable); evicted by LRU |
| Redis | `avail:{tenantId}` | 30s | **Event-driven** on `MenuAvailabilityChanged` |
| Browser | Both, per headers | — | — |

**Availability invalidation is event-driven, not TTL-driven.** When a barista 86s oat milk from the KDS (FR-3.9), the `catalog` context emits `MenuAvailabilityChanged`; the subscriber deletes `avail:{tenantId}`. The 30-second TTL is a backstop for a missed event, not the mechanism.

**Warming**: publishing a menu revision (FR-10.12) pre-renders and caches the new version inside the publish transaction's commit hook, so the first customer after a publish does not pay the assembly cost.

## 5. Edge cases

| Case | Behaviour |
|---|---|
| Item 86'd between menu load and quote | Quote returns it in `unavailable[]`; webview marks it and blocks checkout (FR-2.7) |
| Modifier 86'd but item available | Only the option is disabled. **Oat milk runs out before lattes do** — this is why they are 86-able independently |
| Required group has all options 86'd | The whole item is treated as unavailable, computed server-side at quote |
| Menu version not found | `409 MENU_VERSION_GONE`. Versions retained 30 days |
| `ar-EG` name missing | Falls back to `en`. Never renders blank (FR-9.1) |
| Empty category | Omitted from the payload entirely |
| Stale CDN edge after publish | Impossible — the URL changed |

## 6. Performance budget

The menu is the largest asset on the ordering path and NFR-9/10 are the hardest targets in the plan.

| Constraint | Limit |
|---|---|
| Menu payload, gzipped | **≤ 80 KB** for a 60-item menu. CI fails a fixture exceeding it |
| Availability payload | ≤ 2 KB |
| Cold menu load | One CDN hit, no API round-trip |
| Warm load, same version | Zero network for the menu; availability only |

If a café's menu ever exceeds the budget, the fix is pagination by category — **not** a looser budget. Recorded here so the decision is not made under pressure later.

---

## 7. Tests

**Unit** — locale fallback; modifier group dereferencing; price resolution picks the row with `valid_to IS NULL`.

**Integration** — publishing a revision mints a new version id and leaves the previous resolvable; 86-ing emits the event and evicts the Redis key; a required group with every option 86'd renders the item unavailable.

**Contract** — the menu response is byte-identical across two fetches of the same version (this is what makes `immutable` safe to claim).

**Performance** — a 60-item fixture menu stays inside 80 KB gzipped, asserted in CI.
