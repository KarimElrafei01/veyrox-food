# F1.1 — Session & Entry

QR scan → WhatsApp → inbound webhook → greeting with CTA → signed session token → webview opens.

**Traces to**: FR-1.1–1.7, FR-2.1–2.5 · DEC-01 (one store QR) · ADR-0003 · ADR-0016 (Fiwano).

---

## 1. Flow

```
1. Customer scans the store QR (one per café, not per table)
     → https://wa.me/<number>?text=<greeting + store token>
2. WhatsApp opens with the text PRE-FILLED. Customer must tap send.  ← FR-1.2
3. Fiwano → POST /webhooks/whatsapp
     verify signature on raw bytes → dedupe on provider message id
     → INSERT inbound_events → enqueue → 200 in <500ms      ← NFR-8
4. Worker: resolve tenant from phone_number_id
     → resolve or create customer from wa_id
     → check store hours, feature flags, no-show suppression
     → mint session token
5. Worker sends greeting with a CTA-URL button:
     https://order.veyroxai.com/s/<token>
6. Webview opens → GET /public/session/:token
```

**Step 2 is a hard platform constraint.** No link can send on a user's behalf. The prefilled text reduces it to one thumb tap with no typing, but it is not zero — and scan-to-send drop-off is invisible to us, because a scan that never sends produces no webhook.

## 2. Session token

Stateless, HMAC-signed. No server-side session store — which is what lets the API scale horizontally with no sticky sessions or shared state.

```
veyrox.v1.<base64url(payload)>.<base64url(hmac_sha256(payload, SESSION_KEY))>
```

```json
{
  "t": "tenant_uuid",
  "c": "customer_uuid",
  "w": "wa_id",
  "m": "menu_version_uuid",
  "r": "silver",
  "l": "en",
  "iat": 1757160000,
  "exp": 1757160900
}
```

| Property | Rule | Why |
|---|---|---|
| TTL | **15 minutes** | Long enough to browse and order, short enough that a forwarded link is near-worthless |
| Menu version | **Pinned at mint time** | The customer's prices cannot change mid-cart, even if the owner publishes a revision (FR-10.12) |
| Loyalty tier | **Pinned at mint time** | Quote can apply tier perks without a customer lookup; collection is the only way a tier changes, so the 15-minute staleness bound is acceptable |
| Personal data | **None in the clear** | A screenshot of the URL leaks a tenant id and an opaque customer id, nothing more |
| Privilege | **Read + place-order only** | Cannot reach `/staff/*`, cannot pay, cannot void |
| Verification | Constant-time compare, before parsing | Standard, and prevents a timing oracle on the signature |

**Key rotation**: `SESSION_KEY` supports two active keys — sign with the current, verify against both. A rotation is then a deploy, not an outage for anyone mid-cart.

### Tab restoration

After a successful resolve from the CTA URL, the webview stores the opaque customer
token in `sessionStorage` only, bounded to 2,048 characters. This lets a refresh of an
internal route such as `/pairings` re-resolve the session without retaining the token
after the browser tab closes. The client never decodes or trusts the stored value: it
always calls `GET /public/session/:token` again before it renders customer data.

The token is never put in `localStorage` or a cookie. The client clears it when the API
returns `SESSION_EXPIRED`, `SESSION_INVALID`, or `WHATSAPP_ORDERING_DISABLED`; temporary
network and store-closed failures retain it so a customer can retry within the 15-minute
server TTL. A direct internal URL without a usable tab token shows the standard reopen
session state rather than a perpetual loader.

## 3. API

### `GET /public/session/:token`

The webview's first call. Returns everything needed to render the menu shell without a second round-trip.

    "timezone": "Africa/Cairo"

  "session": {
    "menuVersion": "8a2e…",
    "expiresAt": "2026-09-06T15:45:00+03:00",
    "locale": "en"
  },
  "customer": {
    "displayName": "Karim",

`links.menu` is returned rather than constructed client-side, so the version pin is server-controlled and the client cannot request a version it was not granted.

**Response 409 — store closed**

```json
{

  "status": 403,
  "code": "ORDERING_SUSPENDED",

```

Other failures: `401 SESSION_EXPIRED`, `401 SESSION_INVALID`, `403 WHATSAPP_ORDERING_DISABLED`.

## 4. Data access

Session resolve is **three indexed point lookups**, all sub-millisecond:

```sql
-- 1. tenant, from the token's tenant id (PK)
-- 2. customer, from the token's customer id (PK)
-- 3. open-order + suppression check
SELECT ... FROM orders
WHERE tenant_id = $1 AND customer_id = $2
  AND status IN ('placed','received','preparing','ready');
```

Store-hours evaluation is pure computation from `store_hours` + `store_closures`, both cached per tenant in Redis (`hours:{tenantId}`, TTL 300s, invalidated on settings write).

```sql
customers (tenant_id, phone_hash) UNIQUE     -- webhook-time customer resolve
tenants   (qr_token) UNIQUE                  -- store token → tenant
tenants   (qr_token_previous) WHERE qr_token_previous IS NOT NULL   -- FR-1.5 grace window
orders    (tenant_id, customer_id, status)
            WHERE status IN ('placed','received','preparing','ready')
```

The last index is partial and therefore tiny — it holds only in-flight orders, so the open-order check is an index-only scan of at most a handful of rows no matter how long the café has been trading.

## 5. Caching

| Data | Where | TTL | Invalidated by |
|---|---|---|---|
| Tenant profile | Redis `tenant:{id}` | 300s | Settings write |
| Store hours + closures | Redis `hours:{id}` | 300s | Settings write |
| Resolved feature state | Redis `flags:{tenantId}` | 30s | Flag change (NFR-57) |
| Session response | **Not cached** | — | Per-customer, carries live tier and balance |

`points_cache` is read directly from `customers` rather than summed from `loyalty_ledger` — it is maintained transactionally and guarded by INV-4, so display costs one column read (F1.5 §3).

## 6. Edge cases

| Case | Behaviour |
|---|---|
| Token expired mid-browse | `401 SESSION_EXPIRED`. Webview clears its tab-scoped token and shows "session expired, tap to reopen" with a `wa.me` link. Cart is preserved in `sessionStorage` and restored if the new session pins the same `menuVersion` |
| Store closes while browsing | Placement fails `409 STORE_CLOSED`. Browsing is not blocked — a closed café can still show its menu |
| Menu published mid-session | Session keeps its pinned version. No price changes under the customer |
| Pinned version garbage-collected | `409 MENU_VERSION_GONE` → client re-resolves session. Versions are retained 30 days, far beyond a 15-minute TTL |
| Customer messages twice quickly | `inbound_events` dedupes on provider message id; only one greeting is sent |
| Rotated `qr_token` | Old token resolves for 30 days and logs a warning (FR-1.5). With one store QR, rotation invalidates every printed copy at once — so the grace matters more, not less |
| Unknown/absent store token | Resolve by `phone_number_id` alone. The token is a hint, never an authorization |

## 7. Tests

**Unit** — token mint/verify round-trip; expiry boundary at exactly `exp`; tampered signature rejected; verification under both keys during rotation; store-hours evaluation across midnight and across a DST boundary.

**Integration** — session resolve returns correct tier and balance; open-order cap blocks a second session's placement; suppression returns `ORDERING_SUSPENDED`; closed store returns `opensAt` in tenant-local time.

**Contract** — replay the Fiwano/Meta inbound corpus including a **duplicate delivery**; assert exactly one greeting is sent (`07-test-and-quality-strategy.md` §5).

**Browser integration** — after resolving a CTA token, reload `/menu`, `/pairings`, and
`/checkout`; each must re-verify the tab token before rendering. An expired, invalid, or
disabled response clears that token and presents the reopen-session state.

**Manual, every ordering-path change** — open the CTA link inside WhatsApp's in-app browser on iOS and Android (NFR-45).
