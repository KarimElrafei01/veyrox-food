# F1.6 — Order Placement

The only write in F1. Draft cart → `placed` order visible to the kitchen.

**Traces to**: FR-2.14–2.18, FR-2.23–2.26 · ADR-0010 (no payment, accept gate) · GAP-18.

---

## 1. What placement does and does not do

| Does | Does **not** |
|---|---|
| Re-price server-side from the pinned menu version | Take payment — there is no PSP (ADR-0010) |
| Enforce the no-show gates | **Deduct materials** — that is barista Accept (F2) |
| Snapshot price, cost, recipe version, names | Accrue loyalty points — that is collection (F3) |
| Insert order + lines + modifiers + event, in one transaction | Send the confirmation inline — it is enqueued |
| Emit `OrderPlaced` → SSE → KDS "New" column | Start the ETA clock |

**Materials are not deducted here, and that is the whole design.** An order nobody has accepted has consumed nothing, so a spam order, a mis-tap, or a change of mind costs the café exactly zero. That is what replaces the commitment prepayment used to provide (GAP-18).

## 2. API

### `POST /public/orders`

**Request** (session token in `Authorization`)

```json
{
  "idempotencyKey": "01927f3a-…",
  "items": [
    { "menuItemId": "i1…", "qty": 2, "modifierOptionIds": ["m_large", "m_oat"] }
  ],
  "expectedTotalMinor": 27500,
  "tableLabel": null,
  "customerNote": "no sugar"
}
```

- `idempotencyKey` — client-generated UUIDv7, **required**.
- `expectedTotalMinor` — **advisory**. Not trusted as a price; used only to detect that the customer was looking at a stale total.
- `tableLabel` — only when `ordering.askTableNumber` is on (FR-1.7). Free text, max 16 chars, never a foreign key.
- `customerNote` — max 140 chars, shown on the ticket, never parsed.

**Response 201**

```json
{
  "orderId": "o_9f2…",
  "orderNumber": "A-047",
  "status": "placed",
  "totalMinor": 27500,
  "payAt": "counter",
  "eta": { "lowerMinutes": 8, "upperMinutes": 12, "startsOnAccept": true,
           "promisedLowerAt": null, "promisedUpperAt": null },
  "loyalty": { "pointsToEarn": 33 },
  "placedAt": "2026-09-06T15:31:12+03:00",
  "traceId": "0af7651916cd43dd"
}
```

`orderNumber` is a short per-tenant, per-day sequence (`A-047`) — what staff shout across a counter. `orderId` is the UUID everything else keys on.

**Response 409 — price changed**

```json
{
  "code": "PRICE_CHANGED", "status": 409,
  "detail": "The price changed while you were ordering.",
  "quote": { /* full fresh quote body, F1.3 §2 */ }
}
```

The fresh quote is returned inline so the client re-renders and asks for confirmation in one round-trip rather than two.

**Response 409 — open order limit** (FR-2.23)

```json
{
  "code": "OPEN_ORDER_LIMIT", "status": 409,
  "detail": "You already have an order in progress.",
  "existingOrder": { "orderId": "o_8b1…", "orderNumber": "A-041", "status": "ready" }
}
```

Returning the existing order matters: the customer's likely reaction is *"where is my other order?"*, and this answers it without a support message.

**Other**: `403 ORDERING_SUSPENDED` (FR-2.25) · `409 STORE_CLOSED` · `409 ITEM_UNAVAILABLE` · `422 MIN_ORDER_VALUE` · `422 MODIFIER_*` · `401 SESSION_*`.

**Replay**: same `idempotencyKey` → `200` with the original body and `Idempotency-Replayed: true`. Never `409` — a retry after a timeout is the normal case, not an error.

## 3. Server sequence

```
1. Verify session token; load pinned menuVersion
2. Gate: whatsapp_ordering enabled → resolveFeature()
3. Gate: store open  → else STORE_CLOSED
4. Gate: no-show suppression → else ORDERING_SUSPENDED
5. Gate: open-order cap → else OPEN_ORDER_LIMIT
6. Re-check availability → else ITEM_UNAVAILABLE (with ids)
7. domain.priceCart()  — the SAME call /quote makes
8. If expectedTotalMinor present and differs → PRICE_CHANGED + fresh quote
9. Gate: total ≥ minOrderValueMinor → else MIN_ORDER_VALUE
10. BEGIN
      INSERT orders                     (status='placed', idempotency_key)
      INSERT order_items                ← six snapshot columns
      INSERT order_item_modifiers       ← name + delta snapshots
      INSERT order_events               (null → placed, actor=customer)
    COMMIT
11. Commit hook: emit OrderPlaced
      → SSE to KDS "New"      (ADR-0005)
      → enqueue confirmation message
```

**Gates before the transaction, effects after commit.** Nothing is enqueued or streamed until the row is durable — a rolled-back placement must never produce a WhatsApp message or a ticket on the board.

### The snapshots

`order_items` freezes six columns at placement:

```
unit_price_minor · modifier_total_minor · line_total_minor
cost_snapshot_minor · recipe_version_id · menu_price_version_id
name_snapshot_en · name_snapshot_ar
```

`cost_snapshot_minor` and `recipe_version_id` are written **here**, not at Accept, even though materials are deducted at Accept. The order must record what the recipe *was* when the customer ordered it. If the owner edits the recipe in the two minutes before the barista taps Accept, the deduction uses the version stamped here — which is what makes the void negation exact (`04-data-model.md` §1) and last month's margin report stable (NFR-19).

## 4. The no-show gates

Prepayment used to make the customer carry the no-show risk. Without it the café does, so three gates bound it (GAP-18, ADR-0010).

### Open-order cap — `ordering.max_open_orders`, default 1

```sql
SELECT id, order_number, status FROM orders
WHERE tenant_id = $1 AND customer_id = $2
  AND status IN ('placed','received','preparing','ready')
LIMIT $3;

-- orders (tenant_id, customer_id, status)
--   WHERE status IN ('placed','received','preparing','ready')
```

Partial index, so this is an index-only scan of at most a few rows regardless of history. Bounds a single bad actor to one drink.

### No-show step-down — 3 abandonments in 90 days

```sql
SELECT count(*) FROM orders
WHERE tenant_id = $1 AND customer_id = $2
  AND status = 'abandoned' AND created_at > now() - interval '90 days';

-- orders (tenant_id, customer_id, created_at DESC) WHERE status = 'abandoned'
```

Result cached in Redis `noshow:{tenantId}:{customerId}` for 300s — it changes at most once a day per customer, so re-counting per placement is waste. Invalidated on `OrderAbandoned`.

Deliberately generous: a real customer will not reach three abandonments by accident, and the owner can reverse a step-down from the Store Console.

### Availability re-check

Between menu load and placement a barista may have 86'd something. Re-checked against Redis `avail:{tenantId}`, and the response names the offending ids so the webview can correct the cart rather than just failing.

## 5. Idempotency

```sql
orders (tenant_id, idempotency_key) UNIQUE
```

On conflict, load the existing order and return its original response body. **The stored response is returned, not a re-derived one** — a re-derivation could differ if the queue moved, and a replay must be byte-identical.

This covers three real cases: a customer double-tapping "Place order"; a client retrying after a timeout where the first request actually succeeded; and a flaky mobile connection resending. All three are normal, none are errors.

## 6. Edge cases

| Case | Behaviour |
|---|---|
| Two devices, same session token | Second gets `OPEN_ORDER_LIMIT` — the cap does the work |
| Store closes between quote and placement | `409 STORE_CLOSED`. The gate is at placement, not at quote |
| Menu published between quote and placement | Session stays pinned. Prices do not move under the customer |
| Item 86'd between quote and placement | `409 ITEM_UNAVAILABLE` with ids |
| `expectedTotalMinor` omitted | Placement proceeds at the server total. The field is optional |
| `expectedTotalMinor` wrong by 1 piastre | `PRICE_CHANGED`. Exact comparison — a tolerance would hide a rounding bug, which is exactly what it would be |
| Session expires mid-request | Verified at entry; a request already in flight completes |
| Customer suspended between session and placement | Gated at placement. Session resolve is not a licence |

## 7. Observability

| Signal | Purpose |
|---|---|
| `orders_placed_total{tenant,channel}` | Café Health dashboard |
| `order_placement_rejected_total{code}` | Which gate is firing. A spike in `OPEN_ORDER_LIMIT` means abandonments, not abuse |
| `order_placement_duration_seconds` | p95 target 300ms (NFR-5) |
| `idempotency_replay_total` | Healthy at low levels; a spike means client retry storms |
| `price_changed_total` | Should be near zero. Non-trivial values mean menus are being published during service hours |

---

## 8. Tests

**Integration** (real Postgres): all four gates independently; idempotent replay returns the **original** body byte-identically; concurrent identical requests produce exactly one order (unique index, under load); **no `material_ledger` rows exist after placement** — this is the test that protects GAP-18's whole premise; a recipe edited between placement and Accept deducts the version stamped at placement.

**Property — PROP-5**: any request replayed N times has the effect of one.

**E2E**: journey 1 — QR → webview → modifiers → place → ticket appears in the KDS New column.
