# F1.5 — Loyalty

Tiers, perks, points preview, and accrual.

**Traces to**: FR-2.10, FR-2.20–2.22 · GAP-06 (clawback) · INV-4 · PRD §8.2.

---

## 1. Tiers

| Tier | Points | Multiplier | Perk |
|---|---|---|---|
| Bronze | 0–150 | 1.0× | — |
| Silver | 151–500 | 1.2× | Free alt-milk |
| Gold | 501+ | 1.5× | Free alt-milk + priority prep |

**Accrual**: `floor(totalMinor / 1000) × multiplier` — 1 point per 10 EGP, rounded down after the multiplier.

**Perks are inherited upward.** `freeForTier: "silver"` means Silver *and above*. Rank comparison, never equality — an equality match silently gives Gold customers fewer perks than Silver, and nobody notices until a Gold customer does.

---

## 2. Where loyalty appears in F1

| Surface | Content | Source |
|---|---|---|
| Session resolve (F1.1) | Tier, balance, points to next tier, perks | Session token + `customers.points_cache` |
| Menu (F1.2) | `freeForTier` on modifier options | Menu payload — data, not logic |
| Quote (F1.3) | `waivedByTier` per modifier; `pointsToEarn` | `domain.priceCart()` + `domain.loyalty` |
| Order placed (F1.6) | `pointsToEarn` (a promise, not a balance change) | Same computation |

**Nothing in F1 writes to the loyalty ledger.** Accrual happens at collection (F3), because payment and collection are the same counter moment (ADR-0010). The webview says *"you will earn 33 points"*; the collection message says *"you earned 33 points"*.

That is a small regression against the PRD's "points update immediately after I order" — and arguably more honest, since the order may still be rejected or abandoned. Recorded in ADR-0010.

### The perk display rule

Quote returns the **real delta plus a waiver flag**, never a zeroed delta:

```json
{ "id": "m_oat", "priceDeltaMinor": 1500, "waivedByTier": true }
```

The customer sees `~~15.00~~ Free` — the perk is *visible*, which is the whole reason a perk exists. Returning `priceDeltaMinor: 0` would silently give away value the customer never notices they received.

The client's rendering is cosmetic. **The server applies the waiver independently at quote and at placement** (F1.3 §3); a client that ignores the flag changes nothing about what is charged.

## 3. Balance: ledger of record, cache for display

Points live in the **append-only `loyalty_ledger`** — never a mutable balance column (`04-data-model.md` §8).

```
loyalty_ledger(id, tenant_id, customer_id, delta, reason, order_id, created_at)
reason ∈ order_accrual | tier_bonus | redemption
       | void_clawback | refund_clawback | manual
```

`customers.points_cache` is a **derived display column**, updated inside the same transaction that appends, and guarded continuously by **INV-4** (`points_cache == Σ loyalty_ledger.delta`).

Why both: F1 reads the balance on every session resolve. Summing a ledger per read is a growing cost per customer forever; a cached column is one already-loaded field. Why the ledger anyway: clawback on void or refund (GAP-06) is a negative row and stays auditable — with a mutable column it is an untraceable decrement, and *"a customer reached Gold on orders that were voided"* is the kind of inconsistency that makes an owner doubt every other number.

```sql
loyalty_ledger (tenant_id, customer_id, created_at DESC)
```

Used for history views and INV-4 verification — not for the hot read, which is the cached column.

## 4. Tier crossing

Detected during accrual (F3), not in F1. Recorded here because F1 renders the result.

- Crossing a threshold enqueues one celebration message — **once per crossing** (FR-2.21).
- A clawback that drops a customer below the threshold does **not** re-fire the message on the next crossing the same day. Idempotency key: `tier_celebration:{customerId}:{tier}:{date}`.
- The new tier applies to the customer's **next session**. The current session's token carries the old tier for at most 15 minutes — correct, since the crossing happened at collection, after this cart was priced.

## 5. Caching

| Data | Where | Notes |
|---|---|---|
| Tier | **Session token** | Signed, ≤15 min stale, zero lookups. Used by `priceCart()` for waivers |
| Balance, points-to-next | `customers.points_cache` | One column on a row already loaded |
| Tier thresholds & multipliers | Redis `settings:{tenantId}` (30s) | Owner-tunable within bounds (FR-10.3) |
| Ledger | **Never cached** | Only read for history and invariant checks |

**Tier in the token is a deliberate staleness trade.** It removes a database read from every quote, and the worst case — a customer who crossed into Silver two minutes ago pays the alt-milk delta on this order — is both rare and self-correcting on the next session.

## 6. Edge cases

| Case | Behaviour |
|---|---|
| Exactly 150 / 151 points | 150 = Bronze, 151 = Silver. Boundary tested on both sides |
| Gold ordering alt-milk | Waived. Gold inherits Silver's perks by rank |
| Loyalty disabled by owner (FR-10.3) | Session returns `tier: null`, no perks, `pointsToEarn: 0`. No waivers applied anywhere |
| Owner changes multiplier mid-session | Bounded setting; takes effect on the next quote. Never retroactive |
| Anonymous counter order | No customer, no accrual. Till orders can attach a customer optionally |
| `points_cache` drifts from ledger | INV-4 fires and **pages**. Never auto-corrected — a drift means a bug, and overwriting the evidence destroys the diagnosis |
| Order rejected or abandoned after placement | No accrual ever occurred; nothing to claw back. This is why accrual is at collection |

---

## 7. Tests

**Unit** (100% branch): accrual at each multiplier; **every tier boundary (150/151, 500/501)** and one either side; rank-based perk inheritance; floor-after-multiply rounding; loyalty disabled.

**Property — PROP-3**: for any sequence of accruals, redemptions and clawbacks, `points_cache == Σ delta` and the derived tier matches the balance. This is INV-4 proven offline, before it can ever fire in production.

**Integration**: a void claws back exactly the accrued points in the same transaction; a clawback crossing a tier boundary downward updates the cached tier; the celebration message fires once per crossing under a replayed event.
